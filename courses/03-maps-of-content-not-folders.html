Part 1 · covers four structures for the same notes

One note, four ways to find it

5 min live

Take one insight note, "Alerts that arrive before any value get muted", and ask where it lives. In a folder it lives in exactly one place. With tags it carries labels, as long as everyone spells them the same way. With links it sits beside the notes it is about. On a map of content it is listed wherever a theme needs it. Andy Matuschak puts the principle in one line: prefer associative ontologies to hierarchical taxonomies, because "often items belong in many places" (read at source).

LiveOne place versus many places3 min▶

Folders give every note exactly one home. That is their strength for files you finish and archive, and their weakness for ideas. Ines filed the insight under Clients/Corvid because that is where she first saw it, and the Dunmore evidence now sits in a different branch that nothing connects. Session 4's bench gives folders some credit: a folder listing does find neighbours, as long as the question happens to match the way you filed.

Tags let a note carry several labels, which beats one folder. The catch is human: tags drift. One month it is #notifications, the next #notifs, and a contractor writes #alerts. Each spelling has its own tag page. Links join notes by idea, the way session 1 built them, but a sparse handful of links gives you very few ways in. Maps of content are notes whose job is to list other notes on one theme, which turns out to be the piece that makes links pay off (Part 2).

Self-studyLuhmann had sections too3 min▶

Luhmann's essay is often quoted as proof that a slip box needs no hierarchy. He did decide "against the systematic ordering in accordance with topics and sub-topics", choosing instead a fixed number for every slip, and wrote that "the fixed filing place needs no system" (Luhmann, "Communicating with Slip Boxes", read).

Yet the archive tells a more mixed story. Johannes Schmidt's 2018 account of the card index (read) describes a first collection of about 23,000 cards in 108 subject sections, and a second of about 67,000 cards under eleven top-level sections with about 100 subsections. Both statements are true at once: Luhmann used broad top-level areas, then refused any taxonomy inside them, where numbering and links took over. People who say "Luhmann used no categories" and people who say "he filed by subject" are each holding half of it. The sources support the split, not either slogan.

For your vault that suggests a modest rule rather than a doctrine: a few broad folders for kinds of file can coexist with maps for themes. What breaks is asking a folder to do a theme's job.

Real world

The finding filed under the wrong client. A familiar pattern: a consultant spots the same problem at a second client, searches the second client's folder, finds nothing, and writes the insight again from scratch. Months later there are two near-identical notes in two folders, each with half the evidence. A theme that crosses clients needs a home that is not a client.

Part 2 · covers hubs and the keyword index

A few ways in, then the links do the rest

5 min live

Luhmann had no search box, so he kept a keyword index. Schmidt (2018, read) reports something surprising about it: for each term it listed "only one to four places". The index did not try to catalogue every card on a topic. It pointed at a handful of entry cards, and from there the links led on. Cards with an above-average number of links, which Schmidt calls hubs, gave access to large parts of the file.

LiveA map is an entry point, not a folder3 min▶

A map of content (MOC) is an ordinary note whose body is links on one theme, usually grouped under a few headings with a line on why each link is there. The term is popularised by Nick Milo's Linking Your Thinking (reported; his pages were not read at source). Functionally it is Luhmann's index entry and Schmidt's hub rolled into one note you can edit: a small number of doors into a theme, after which each member note's own links carry you on.

The difference from a folder is the one that matters for Ines. A note can be listed on as many maps as it belongs to, and listing it moves nothing. The insight stays where it is, and the Corvid map and the notification fatigue map both point at it. Session 4's bench puts a number on the effect: adding maps of content lifts mean recall from 11.5% with idea links only to 84.4% (modelled, computed on a constructed vault). Sparse idea links on their own did worse than folders or tags there; the maps are what made them pay.

Self-studyMaps grow from links, not the other way round3 min▶

Schmidt also describes the opposite of a hub. Poorly linked parts of the file "tend to remain isolated later on and hence fade away", and some parts "seemed to be untouched since their compilation" (Schmidt 2018, read). He calls them black holes. A note nobody links to is, in practice, a note nobody finds.

That sets the order of work. Do not draw up twelve empty maps on day one and then hunt for notes to fill them; that is a folder tree with extra steps. Write and link notes as sessions 1 and 2 taught, and make a map when a theme has enough members that you keep losing track of them. Ten or more notes is a reasonable trigger. The map then records a structure that already exists in the links, and gives it a front door.

Luhmann's own warning applies here as well: "A note that is not connected to this network will get lost" (Luhmann, read). A map rescues only the notes that are on it.

Real world

The index page nobody updates. A familiar pattern: a team wiki opens with a grand contents page listing every document. Within a year half the entries are dead and new pages never got added, because one page was trying to list everything. Small maps that each cover one theme, and that member notes point up to, stay current because each one is small enough to keep.

Part 3 · covers Obsidian's tools for structure

Properties, tags and search: the parts a map is built from

5 min live

Obsidian gives you four tools that work on the same plain files. Properties put structured fields at the top of a note. Tags label notes, nested if you like. Search operators find notes by path, tag, line, section or property. Bases shows notes as database-like views over their properties. Write a field once in a note's front matter and three different readers can use it.

LiveProperties and tags, by the help's rules3 min▶

Properties live in a block at the very start of a file that opens and closes with ---. Each property has a type: Text, List, Number, Checkbox, Date, Date & time or Tags. Obsidian ships three default properties, tags, aliases and cssclasses. Once you give a property name a type, that type applies to that name across the whole vault, so decide early whether theme is Text or List. The help also notes that a hashtag typed inside a text property does not create a tag.

Tags go in the text as #tag or in the tags property as a list. Nest them with a slash, as in #inbox/to-read. Allowed characters are letters, numbers, underscore, hyphen and slash; a tag needs at least one non-numeric character (#1984 is not valid); tags have no spaces and are case-insensitive. Case-insensitive does not mean spelling-insensitive: #Notifications and #notifications are one tag, #notifs is another.

LiveSearch operators that find candidates2 min▶

Obsidian's search accepts operators that narrow a query. The ones a map builder uses most: path: limits to a folder path, tag: finds a tag, line: needs all the words on one line, section: needs them under one heading, and [property:value] matches a property. A nested-tag detail is worth remembering: tag:inbox also matches #inbox/to-read, but tag:#work does not return #myjob/work.

Candidate searches for one themetag:#notifications OR "notification fatigue" path:Insights "notification" line:(muted alerts) [type:insight]

The help lists more operators (file:, content:, block:, task:); check the current help, because search syntax gains options with releases.

Self-studyBases: a view over properties, not a database2 min▶

Bases is a core plugin for what the help calls "database-like views of your notes". The data stays in your Markdown files and their properties; the view is saved as a .base file or embedded in a code block. Layouts include Table, List, Cards, Kanban and Map. For a map of content, a Table of every note with type: insight and a theme column is a fast way to spot members you forgot to list.

That is as far as Bases goes here. Running clients, projects and invoices from database records is a different job, and Ines does it in Notion ↗. Bases is new and changes often, so check the current help before relying on a menu name.

Pick a few properties and keep them. Three fields used on every note (type, theme, up) beat twelve used now and then. A property only helps a search or a view if it is filled in on the notes you are looking for.

Build-along

Ines's notification fatigue map

★ 22 min · everyone builds

Build one map of content for one theme in your own vault. Ines's constructed map is the worked example: four headed sections of links, each with a sentence saying why, and member notes that point back up to it through a property. Swap in a theme from your own work if you have one with ten or more notes.

Choose one theme with ten or more notes. A theme is an idea that crosses projects, not a project or a client. Write down its name and a rough count before you start; the count tells you whether it deserves a map yet.

★ Step 1 · pick the themeTheme notification fatigue Seen at Corvid Studio, Dunmore District Council Rough count 10+ notes (interviews, readings, insights) Not a theme "Corvid Studio" (a client: a folder can do that)

Search for candidates with operators. Open Search and run a few queries. Tag spellings drift, so search the phrase as well as the tag, and try a folder path where insights live. Note every hit that is really about the theme.

★ Step 2 · candidate searchestag:#notifications OR "notification fatigue" path:Insights tag:#notifs OR tag:#alerts [type:insight]

Create the map note with headed sections. Name it after the theme with "(map)" on the end, so it never collides with the theme's own idea note. Give it a few headings and, under each, wikilinks with one sentence saying why the note belongs. The sentence is what turns a list into a map.

★ Step 3 · Notification fatigue (map).md## Insights - [[Alerts that arrive before any value get muted]]: the core pattern, two clients. - [[Value after effort]]: why the timing matters. ## Readings - [[Reading - notification design]]: the guidance Ines checks claims against. ## Evidence by client - Corvid: [[2026-09-15 Corvid interview P18]]: muted on day two. - Dunmore: [[Dunmore interview P11]]: "pure notification fatigue". ## Open questions - Does muting predict churn? No evidence yet.

Point each member note up to the map. Add an up property to every note you listed. A link inside a property is written as a wikilink in quotes, because unquoted square brackets mean a list in YAML. Links in properties are a newer feature: check the current help for how your version shows them in backlinks and the graph.

★ Step 4 · front matter on each member note--- type: insight theme: notification fatigue up: "[[Notification fatigue (map)]]" tags: - notifications ---

Optional: a Bases table of insight notes. If Bases is on (Settings, Core plugins; check the current help for the exact menu), create a new base, filter to notes whose type is insight, and show theme and up as columns. Any row about the theme with an empty up is a member the map is missing.

★ Step 5 · a view, saved as a fileFile Insights.base Layout Table Filter type is insight Columns file name · theme · up Look for theme = notification fatigue AND up is empty

Record the finding. Count what the map holds and, more importantly, what it still misses. Notes that mention the theme but carry no up and are not listed are exactly the ones the map cannot help.

★ Step 6 · the finding (your numbers will differ)Notes listed on the map ___ Members with an up: property ___ Search hits still not linked up ___ The unlinked ones are usually unprocessed interviews.

A map helps only the notes that link to it. On session 4's bench, with maps in place, eleven of twelve questions are answered. The one that fails starts from an interview Ines never processed, so it links to no map and the routes never reach it (modelled, computed on a constructed vault). Linking a note up to its map is part of finishing the note, not a tidy-up for later.

Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · Ines's notification fatigue evidence comes from two clients. Why does a map of content serve the theme better than a folder?

A folder is one place per note. The Corvid and Dunmore interviews can stay in their client folders while the map lists both, along with the insight and the readings. Listing moves nothing and copies nothing.

2 · According to Schmidt (2018), what did Luhmann's keyword index do?

The index was deliberately thin: a few doors per term. From an entry card, links and hubs led into the rest of the file. A map of content plays the same role, which is why it can stay short.

3 · Which search finds a note tagged #inbox/to-read?

The help says tag:inbox matches nested tags under inbox, including #inbox/to-read. path: looks at folders, not tags, and the order of a nested tag matters. Watch the other direction too: tag:#work does not return #myjob/work.
